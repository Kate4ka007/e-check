# Конвейер распознавания

Как изображение чека превращается в структурированные данные.

Это ядро продукта: от качества этого конвейера зависит ответ на гипотезу проекта.

Связанные решения: [ADR-0003](adr/0003-async-processing.md) (асинхронность),
[ADR-0004](adr/0004-provider-abstraction.md) (интерфейс провайдера),
[ADR-0010](adr/0010-deterministic-confidence.md) (уверенность),
[ADR-0011](adr/0011-free-tier-first.md) (бесплатные модели).

---

## 2. Подготовка изображения

Выполняется частично на клиенте, частично на сервере.

### На клиенте, до отправки

Уменьшение до 2000 px по длинной стороне и перекодирование в JPEG качества 85.
Фотография с телефона весит 4–8 МБ, после уменьшения — около 300 КБ. Это ускоряет
загрузку на мобильной сети в разы, а на распознавании не сказывается: текст чека
читается и в таком разрешении.

Применение поворота из EXIF. Иначе снятый вертикально чек уедет боком, и модель
будет читать повёрнутый текст.

Оригинал на сервер не отправляется. Он не нужен: пользователь смотрит на изображение
только чтобы сверить данные.

### На сервере, после загрузки

Проверка настоящего типа файла по сигнатуре, а не по заголовку `Content-Type`
и не по расширению. Оба задаются клиентом и не заслуживают доверия.

Конвертация HEIC/HEIF в JPEG. Это формат камеры iPhone по умолчанию, и без
конвертации значительная часть пользователей просто не сможет загрузить чек.
Обрабатывается на сервере, потому что браузеры HEIC не декодируют.

Генерация уменьшенной копии 400 px для списков.

### Форматы

| Формат      | Приём | Примечание                       |
| ----------- | ----- | -------------------------------- |
| JPEG        | да    | основной                         |
| PNG         | да    | скриншоты чеков из приложений    |
| WEBP        | да    |                                  |
| HEIC / HEIF | да    | конвертируется в JPEG на сервере |
| PDF         | нет   | после MVP: электронные чеки      |

Ограничения: до 15 МБ, не менее 200 px по короткой стороне, соотношение сторон
не более 1:10. Последнее отсекает случайные снимки, но пропускает длинные чеки —
они действительно бывают вытянутыми.

Все значения задаются конфигурацией, не константами в коде.

## 3. ReceiptExtractor

Единая точка входа в распознавание. Доменная логика знает только этот интерфейс.

```ts
interface ReceiptExtractor {
  readonly kind: 'vision' | 'two-stage' | 'mock'
  extract(input: ExtractionInput): Promise<ExtractionResult>
}

interface ExtractionInput {
  imageBuffer: Buffer
  mimeType: string
  hints?: {
    expectedCurrency?: string // baseCurrency пользователя
    knownMerchants?: string[] // магазины из истории пользователя
  }
}

interface ExtractionResult {
  data: ParsedReceipt // прошло проверку схемой
  raw: unknown // сырой ответ, уходит в хранилище
  meta: {
    model: string
    durationMs: number
    costMicros: number
    attempt: number
  }
}
```

`hints` заметно повышают качество: список магазинов, где пользователь уже
покупал, помогает модели опознать искажённое название, а ожидаемая валюта
снимает неоднозначность там, где на чеке символа валюты нет.

### Реализации

**`VisionExtractor`** — изображение отправляется vision-модели, ответ приходит
структурированным за один вызов. Модель видит расположение колонок и выравнивание,
то есть ту информацию, которую двухэтапный вариант теряет.

**`TwoStageExtractor`** — композиция `OcrProvider` и `ReceiptParser`. OCR отдаёт
текст, текстовая модель его разбирает. Дешевле по токенам, даёт координаты
блоков, но структура строки восстанавливается по догадке.

```ts
interface OcrProvider {
  recognize(input: OcrInput): Promise<OcrResult>
}

interface ReceiptParser {
  parse(input: { rawText: string; blocks?: OcrBlock[] }): Promise<ParsedReceipt>
}
```

**`MockExtractor`** — возвращает заранее заданный результат по хешу файла.
Используется в тестах и при отладке интерфейса, чтобы не тратить лимиты.

Выбор реализации — переменная окружения `EXTRACTOR_KIND`. Какая победит,
решается по результатам M0.

## 4. Контракт с моделью

### Схема ответа

Определена Zod-схемой в `packages/contracts` и передаётся модели как JSON Schema
через structured output. Той же схемой проверяется ответ — см. [ADR-0009](adr/0009-zod-first-contracts.md).

```ts
const ParsedReceiptSchema = z.object({
  merchant: z
    .object({
      name: z.string().min(1).max(200),
    })
    .nullable(),

  purchasedAt: z
    .string()
    .regex(/^\d{4}-\d{2}-\d{2}$/)
    .nullable(),
  purchasedTime: z
    .string()
    .regex(/^\d{2}:\d{2}$/)
    .nullable(),
  currency: z.string().length(3).nullable(),

  items: z
    .array(
      z.object({
        name: z.string().min(1).max(300),
        lineType: z.enum(['ITEM', 'DISCOUNT', 'DEPOSIT', 'DEPOSIT_RETURN', 'FEE']),
        quantity: z.number().positive().default(1),
        unit: z.enum(['PCS', 'KG', 'G', 'L', 'ML', 'M']).default('PCS'),
        unitPriceMinor: z.number().int().nullable(),
        totalPriceMinor: z.number().int(),
        categorySlug: z.enum(CATEGORY_SLUGS),
        rawText: z.string().nullable(),
      }),
    )
    .max(200),

  subtotalMinor: z.number().int().nullable(),
  taxTotalMinor: z.number().int().nullable(),
  discountTotalMinor: z.number().int().nullable(),
  totalMinor: z.number().int().nullable(),
})
```

Ключевые моменты:

**Суммы запрашиваются сразу в минорных единицах.** Модель просят вернуть `278`,
а не `2.78`. Это убирает разбор дробных чисел с их локальными разделителями —
`2,78` против `2.78` — и исключает потерю точности.

**`categorySlug` — закрытое перечисление.** Без этого модель изобретает новые
названия категорий на каждом чеке, и сопоставление с базой не работает.
Список передаётся в промпте.

**Всё, что может отсутствовать, объявлено `nullable`.** Модель должна иметь
возможность честно сказать «не вижу», а не выдумывать значение. Это важнее,
чем кажется: выдуманная дата хуже отсутствующей, потому что её никто не проверит.

**Количество позиций ограничено.** Защита от зацикливания модели на длинном чеке.

### Промпт

Хранится в версионируемом файле, а не в строке в коде. Версия записывается
в `ProcessingJob`, чтобы при падении качества было видно, какое изменение
промпта его вызвало.

Структура системного сообщения:

1. Роль: извлечь данные из изображения чека.
2. Правила по суммам: минорные единицы, целые числа.
3. Правила по датам: ISO, при двусмысленности предпочесть европейский формат.
4. Список категорий с краткими пояснениями.
5. Правила по типам строк: как отличить скидку, депозит и сбор от покупки.
6. Требование не выдумывать: отсутствующее возвращать как `null`.

### Защита от инъекций

Текст на изображении — это данные, а не инструкции. Чек может содержать
надпись вида «игнорируй предыдущие инструкции». Вероятность случайной атаки
низкая, но защита ничего не стоит:

- изображение и распознанный текст передаются только в пользовательском
  сообщении, никогда в системном;
- ответ вне схемы отбраковывается независимо от содержания;
- в промпте явно указано, что текст на изображении — данные для извлечения.

Главная защита структурная: модель физически не может вернуть ничего, кроме
объекта заданной схемы, а всё, что она вернула, проходит проверки целостности
из [DATA_MODEL.md](DATA_MODEL.md).

## 5. Отказы и повторные попытки

### Классификация

| Причина                           | Повторять    | Действие                         |
| --------------------------------- | ------------ | -------------------------------- |
| `429` — превышен лимит            | да           | следующая модель, затем пауза    |
| `404` — модель недоступна         | да           | сразу следующая модель           |
| `5xx` у провайдера                | да           | пауза с увеличением              |
| Таймаут                           | да           | пауза с увеличением              |
| Сеть                              | да           | пауза с увеличением              |
| Ответ не прошёл схему             | да, один раз | повтор с уточнением              |
| `401` — ключ неверен              | нет          | `FAILED`, оповещение в Sentry    |
| Изображение отклонено провайдером | нет          | `FAILED`, сообщение пользователю |
| Попытки исчерпаны                 | —            | `FAILED`                         |

### Перебор моделей

Бесплатные модели ротируются: работавшая вчера сегодня возвращает
`404 No endpoints found`. Поэтому конфигурация задаёт список кандидатов:

```text
EXTRACTOR_MODELS=model-a:free,model-b:free,model-c:free
```

При `404` или `429` — сразу следующая модель без паузы; исчерпав список,
worker выдерживает паузу и начинает заново. Фактически ответившая модель
записывается в `ProcessingJob.providerModel`.

Паузы между попытками: 2, 8, 30 секунд, со случайным разбросом, чтобы
одновременно упавшие задачи не пошли на повтор синхронно.

### Что видит пользователь

Перебор моделей и повторные попытки не показываются. Пока попытки не исчерпаны,
статус остаётся `PROCESSING` — рассказывать о внутренних отказах нечего.

При окончательном отказе — понятное объяснение и два действия на выбор:
попробовать снова или ввести вручную. Технический код ошибки скрыт, но
доступен в деталях для отладки.

## 6. Нормализация

Между ответом модели и сохранением данные приводятся к согласованному виду.

**Валюта.** Если модель не определила — берётся `baseCurrency` пользователя.
Код проверяется по ISO 4217.

**Дата.** Проверяется на разумность: не в будущем более чем на день (часовые
пояса), не старше десяти лет. Неразумная отбрасывается в `null` — пусть
пользователь введёт сам, чем в аналитику попадёт мусор.

**Магазин.** Название нормализуется и сопоставляется с существующими у этого
пользователя. При совпадении — привязка к существующей записи, иначе создание новой.

**Категории.** `categorySlug` сопоставляется с записью в базе. Неизвестное
значение — в `other`, с записью в лог: систематические промахи означают, что
надо править промпт.

**Позиции.** Проверяется соответствие `quantity × unitPrice ≈ totalPrice`.
При расхождении `totalPrice` считается верным — он на чеке напечатан крупно
и распознаётся надёжнее.

**Итог.** Если модель не вернула `totalMinor`, но вернула позиции — итог
считается как их сумма. Обратное неверно: недостающие позиции не выдумываются.

## 7. Расчёт уверенности

Реализация [ADR-0010](adr/0010-deterministic-confidence.md). Уверенность
вычисляется из проверяемых сигналов; модель о ней не спрашивают.

### Итоговая сумма

| Условие                                            | Уровень  |
| -------------------------------------------------- | -------- |
| Сумма позиций сходится с итогом в пределах допуска | `HIGH`   |
| Расхождение до 5%                                  | `MEDIUM` |
| Расхождение больше 5% или позиций нет              | `LOW`    |

### Дата

| Условие                                      | Уровень  |
| -------------------------------------------- | -------- |
| Разбирается однозначно, в разумном диапазоне | `HIGH`   |
| День и месяц оба ≤ 12 — формат неоднозначен  | `MEDIUM` |
| Не разобрана или вне диапазона               | `LOW`    |

### Магазин

| Условие                                        | Уровень  |
| ---------------------------------------------- | -------- |
| Нормализованное имя уже есть у пользователя    | `HIGH`   |
| Новое имя, но выглядит осмысленно              | `MEDIUM` |
| Не распознано или состоит из мусорных символов | `LOW`    |

### Позиция

Начинает с `HIGH` и понижается за каждый признак:

```text
quantity × unitPrice не равно totalPrice
название короче 3 символов или состоит из цифр
цена более чем в 10 раз выше медианы по чеку
категория определена как other
```

### Уверенность чека

Минимум из уверенностей магазина, даты и итога. Уверенность позиций
на общую оценку не влияет — она показывается у самих позиций.

## 8. Кэширование

Результат распознавания кэшируется по `fileSha256`. При повторной обработке
того же файла провайдер не вызывается.

На бесплатном тарифе с лимитом 50 запросов в день это принципиально:
без кэша отладка промпта на одном и том же чеке съедает дневную квоту
за полчаса.

Кэш сбрасывается при смене версии промпта или модели — иначе после правки
промпта результат не изменится, и будет непонятно, почему.

## 9. Ограничения и стоимость

| Ограничение                         | Значение             | Зачем                      |
| ----------------------------------- | -------------------- | -------------------------- |
| Загрузок на пользователя в час      | 30                   | защита от случайного цикла |
| Одновременных задач на пользователя | 3                    | справедливое распределение |
| Задач в день на инсталляцию         | по лимиту провайдера | не упереться внезапно      |
| Таймаут одной попытки               | 60 с                 | не держать задачу вечно    |
| Таймаут задачи целиком              | 5 мин                | обнаружение зависаний      |

`costMicros` пишется в каждую задачу даже при нулевой стоимости. Это делает
переход на платный тариф прозрачным: стоимость чека известна с первого дня.

## 10. Наблюдаемость

У каждой задачи есть `requestId`, полученный от загрузившего HTTP-запроса
и проходящий через все логи.

Записывается на каждую задачу:

```text
requestId, receiptId, jobId
extractorKind, providerModel, promptVersion
attempt, statusCode, errorCode
durationMs, costMicros
уверенность по полям
```

Не записывается никогда:

```text
изображение чека
распознанный текст
ключи провайдеров
токены сессий
email в открытом виде
```

Сырой ответ провайдера лежит в хранилище с ограниченным сроком жизни,
а не в логах — в логах у него был бы неконтролируемый срок хранения.

### Метрики

```text
receipts_uploaded_total
receipts_processed_total{status}
extraction_duration_ms{extractor,model}
extraction_failures_total{errorCode}
extraction_cost_micros_total
manual_correction_rate
```

Последняя — главная. Она считается при сохранении чека: доля полей с
`source = USER` среди всех заполненных. Именно она отвечает на вопрос
из гипотезы проекта, и именно за ней надо следить после каждого изменения промпта.
