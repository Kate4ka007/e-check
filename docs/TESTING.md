# Тестирование

Стратегия урезана под соло-разработку: тестируется то, где ошибка дорога
или неочевидна. Покрытие ради покрытия не входит в задачи.

---

## 1. Что тестируем и почему

Приоритет определяется ценой ошибки, а не удобством написания теста.

| Область | Почему обязательно | Вид |
|---|---|---|
| Арифметика денег | ошибка тихая и портит все цифры | unit |
| Разделение сумм с округлением | классический источник расхождений на копейку | unit |
| Проверки целостности чека | граница между «предупредить» и «запретить» | unit |
| Инвариант аналитики | разбивка обязана сходиться к итогу | integration |
| Расчёт уверенности | правил много, сломать легко | unit |
| Разбор ответа модели | внешние данные, форма не гарантирована | unit |
| Ограничение по владельцу | утечка чужих данных | integration |
| Дедупликация и идемпотентность | иначе дубликаты в аналитике | integration |
| Переходы состояний чека | гонки между worker'ом и пользователем | integration |
| Сквозной сценарий | ради него всё делается | e2e |

Что **не** тестируем: тривиальные CRUD-обёртки, конфигурацию фреймворка,
вёрстку, геттеры. Тест, который сломается от переименования переменной,
но не поймает ни одной настоящей ошибки, — это обязательство без актива.

---

## 2. Инструменты

| Слой | Инструмент |
|---|---|
| Бэкенд unit и integration | Vitest |
| HTTP-запросы к API | Supertest |
| Фронтенд unit | Vitest |
| Компоненты Vue | Vue Test Utils |
| Сквозные | Playwright |

Vitest вместо Jest и на бэкенде тоже — один конфиг и один синтаксис
на весь монорепозиторий вместо двух.

Testcontainers не используется: тестовая база поднимается той же
`docker compose`, что и для разработки, отдельным сервисом на другом порту.
Для одного разработчика с последовательным запуском тестов этого достаточно,
а зависимость и время старта экономятся. Каждый файл интеграционных тестов
работает в транзакции с откатом.

## 3. Unit-тесты

### Деньги

Первое, что пишется в проекте, — ещё до бизнес-логики.

```text
сложение и вычитание минорных единиц
разделение суммы между позициями: части точно равны целому
разделение с неделимым остатком: лишние единицы у наибольших остатков
форматирование EUR (2 знака), JPY (0), BHD (3)
разбор строк "2,78" и "2.78" в 278
отказ на дробном значении там, где ожидается целое
```

Тест на разделение суммы принципиален: именно он ловит ошибку, при которой
скидка, разложенная по позициям, не сходится с исходной на единицу.

### Проверки целостности

```text
сумма позиций сходится с итогом → без предупреждений
расхождение в пределах допуска  → без предупреждений
расхождение больше допуска      → предупреждение, но сохранение разрешено
отрицательное количество        → ошибка
дата в будущем                  → ошибка
дата десятилетней давности      → ошибка
чек без позиций                 → подтверждение разрешено (ручной ввод)
```

Отдельно проверяется, что мягкие нарушения **не** блокируют сохранение.
Это легко сломать рефакторингом, а последствие — заблокированный пользователь
с обычным чеком.

### Разбор ответа модели

Ответ приходит от внешней системы, форма не гарантирована.

```text
корректный ответ                     → разобран
отсутствующие необязательные поля    → null, без ошибки
неизвестный categorySlug             → other, запись в лог
дробная сумма вместо целой           → отбраковка
позиций больше лимита                → отбраковка
пустой ответ                         → отбраковка
не-JSON                              → отбраковка
инъекция в тексте позиции            → обработана как обычный текст
```

### Уверенность

Каждое правило из [PROCESSING_PIPELINE.md](PROCESSING_PIPELINE.md) —
отдельный тест с граничными значениями.

## 4. Интеграционные тесты

Работают с настоящими PostgreSQL и Redis, с моком провайдера распознавания.

### Ограничение по владельцу

Самый важный интеграционный тест. Проверяет не бизнес-логику, а то,
что расширение Prisma-клиента действительно работает.

```text
пользователь A создаёт чек
пользователь B запрашивает его по id            → 404
пользователь B пытается изменить                → 404
пользователь B пытается удалить                 → 404
список чеков B                                   → чек A отсутствует
аналитика B                                      → суммы A не учтены
экспорт данных B                                 → чек A отсутствует
```

Последние три пункта важнее первых: точечный доступ обычно проверяют,
а вот забыть фильтр в агрегирующем запросе куда легче.

### Инвариант аналитики

```text
для любого набора четов:
  sum(by-category.amountMinor) === summary.totalMinor
```

Проверяется на наборе, включающем неудобные случаи: чек со скидкой на весь
чек, чек без позиций, чек с депозитом за тару, чек, где сумма позиций
превышает итог.

Хороший кандидат на генеративный тест со случайными данными — инвариант
формулируется одной строкой, а случайные комбинации найдут то, что
не пришло в голову.

### Дедупликация и идемпотентность

```text
загрузка того же файла дважды        → один чек, duplicate: true
тот же Idempotency-Key               → тот же ответ, новый чек не создан
тот же ключ с другим файлом          → 409
загрузка после мягкого удаления      → разрешена (частичный индекс)
```

Последний случай легко упустить: без условия `WHERE deleted_at IS NULL`
в индексе пользователь не сможет заново загрузить удалённый чек.

### Обработка

```text
загрузка → задача в очереди → статус PENDING
worker обработал                     → COMPLETED, данные сохранены
провайдер вернул 429                 → повтор, статус остаётся PROCESSING
попытки исчерпаны                    → FAILED, retryable: true
повторная обработка                  → тот же чек, новых не создано
повторная обработка после правок     → поля с source=USER сохранены
повторная обработка CONFIRMED        → статус подтверждения не сброшен
```

## 5. Сквозные тесты

Один сценарий. Тот самый, ради которого делается проект.

```text
регистрация
вход
загрузка тестового изображения чека
ожидание завершения обработки
проверка, что поля заполнены
правка названия позиции и итоговой суммы
сохранение
чек виден в истории
сумма отражена в аналитике
```

Плюс два коротких сценария на ветки, которые ломаются молча:

```text
провайдер отказал → предложен ручной ввод → чек заполнен и сохранён
повторная загрузка того же файла → показан существующий чек
```

Провайдер в сквозных тестах всегда замокан. Реальный сделал бы тесты
медленными, платными и недетерминированными.

### Запуск локально

```bash
docker compose up -d          # postgres, redis, minio
pnpm db:migrate
pnpm test:e2e:install         # один раз: браузер Chromium
pnpm test:e2e
```

Playwright поднимает API (`EXTRACTOR_KIND=mock`), worker и web-сервер.
Нужен Node 22. Если серверы уже запущены с `pnpm dev`, можно переиспользовать
их (`reuseExistingServer`), но worker и API должны работать с mock-экстрактором.

Сценарий: `e2e/main-flow.spec.ts` — регистрация, загрузка, правка позиции,
сохранение, подтверждение, чек в списке.

## 6. Харнесс точности

Отдельный вид проверки, не тест в обычном смысле. Отвечает на вопрос
не «работает ли код», а «работает ли продукт».

### Устройство

Набор реальных чеков с размеченным вручную ожидаемым результатом:

```text
spike/fixtures/
├── private/            реальные чеки, не коммитятся
│   ├── 001.jpg
│   └── 001.expected.json
└── public/             синтетические, для CI
```

Реальные чеки не попадают в репозиторий — это персональные данные.
Для CI используется небольшой синтетический набор.

### Что измеряется

```text
точность по полям: магазин, дата, итог
точность по позициям: доля верно распознанных
доля выдуманных позиций
доля пропущенных позиций
точность категорий
среднее время обработки
средняя стоимость чека
```

### Когда запускается

Вручную после каждого изменения промпта или смены модели. Результат
записывается в таблицу с датой, версией промпта и моделью.

Именно эта таблица отвечает, стало лучше или хуже. Без неё правка промпта —
это гадание: изменение, улучшающее один чек, часто ухудшает пять других.

В CI харнесс не запускается — он требует ключей провайдера и денег.

## 7. Тестовые данные

Фабрики вместо фикстур: функция, создающая чек с разумными значениями
по умолчанию и возможностью переопределить нужное.

```ts
const receipt = await makeReceipt({ totalMinor: 1299, itemCount: 3 })
```

Фикстуры в виде JSON-файлов расходятся со схемой при первой же миграции
и молча теряют смысл.

Обязательные неудобные случаи в наборе:

```text
чек с весовым товаром: 0,532 kg × 2,99
чек с депозитом за тару и его возвратом
чек со скидкой на всю покупку
чек, где сумма позиций не сходится с итогом
чек без позиций (ручной ввод)
чек в валюте, отличной от базовой
чек с сорока позициями
чек с датой в неоднозначном формате (03.04.2026)
```

Эти случаи ломают наивную реализацию. Если они есть в тестах с самого
начала, реализация не будет наивной.

## 8. CI

```text
установка зависимостей
проверка форматирования и линтера
проверка типов
unit-тесты
поднятие postgres и redis
миграции
интеграционные тесты
сборка
сквозные тесты
```

Сквозные тесты — только на `main` и в pull request'ах, не на каждый push
в ветку: они самые медленные, а лимит бесплатных минут не бесконечен.

Ошибки типов, линтера и юнит-тестов — блокирующие. Проваленный сквозной
тест тоже блокирующий, но с возможностью перезапуска: они изредка
падают по независящим причинам.
