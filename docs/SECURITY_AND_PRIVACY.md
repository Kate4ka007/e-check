# Безопасность и персональные данные

Аутентификация, разграничение доступа, защита загрузок, обращение с персональными данными.

Связанные решения: [ADR-0016](adr/0016-hybrid-ssr-public-pages.md) (гибридный рендер: HTML для публичных страниц, SPA за сессией),
[ADR-0012](adr/0012-deferred-privacy-posture.md) (позиция по персональным данным).

---

## 1. Модель угроз

Что реально защищаем, в порядке важности.

**Чужие чеки.** Главный риск. Один пропущенный фильтр по владельцу — и пользователь
видит покупки другого человека. Для приложения о личных финансах это не баг,
а конец проекта.

**Сессии.** Кража токена даёт доступ ко всей истории.

**Провайдер распознавания.** Изображения чеков уходят третьей стороне.
Что она с ними делает — вопрос договора, а не кода. Разбирается в разделе 6.

**Загрузка файлов.** Точка входа, принимающая произвольные байты от анонимного
по сути клиента.

**Стоимость.** Не безопасность в классическом смысле, но неконтролируемый вызов
платного провайдера — это работающая атака на кошелёк.

Что сознательно не защищаем на этом этапе: защиту от целевых атак, аудит
действий администратора, шифрование данных на уровне полей. Приложение
для одного пользователя, работающее локально.

## 2. Аутентификация

### Схема токенов

Access-токен — JWT со сроком жизни 15 минут, в HttpOnly-cookie.
Refresh-токен — случайные 32 байта, срок 30 дней, в HttpOnly-cookie
с путём `/api/v1/auth/refresh`.

```text
Set-Cookie: access_token=...;  HttpOnly; Secure; SameSite=Lax; Path=/;                    Max-Age=900
Set-Cookie: refresh_token=...; HttpOnly; Secure; SameSite=Lax; Path=/api/v1/auth/refresh; Max-Age=2592000
```

Токены недоступны JavaScript — это исключает их кражу через XSS, самый
реалистичный вектор для SPA.

`SameSite=Lax` защищает от межсайтовой подделки запросов для небезопасных
методов. Дополнительный CSRF-токен не нужен, пока фронтенд и API находятся
в одном домене или в поддоменах одного сайта. Если они окажутся на разных
доменах, `SameSite=Lax` перестанет работать и придётся переходить
на `SameSite=None` плюс явный CSRF-токен — это решение принимается при
настройке production-домена, см. [OPERATIONS.md](OPERATIONS.md).

В базе хранится только SHA-256 от refresh-токена. Утечка базы не даёт
готовых к использованию токенов.

### Ротация и обнаружение кражи

Каждый вызов `refresh` выдаёт новую пару и помечает старый токен израсходованным.

Все токены одной сессии связаны полем `family`. Если приходит уже
израсходованный токен, возможны два объяснения: сеть подвела и клиент
повторил запрос, или токен украден и используется параллельно с настоящим.
Различить их нельзя, поэтому реакция консервативная — вся цепочка `family`
отзывается, пользователь входит заново.

```text
вход → T1
T1 → T2   (T1 израсходован)
T2 → T3   (T2 израсходован)
T1 ✗      повторное использование → вся цепочка отозвана
```

Неудобство от редкого повторного входа несопоставимо с последствиями
незамеченной кражи.

### Пароли

Argon2id — устойчив к атакам на видеокартах, в отличие от bcrypt.
Параметры: 19 МБ памяти, 2 итерации, параллелизм 1 (текущие рекомендации OWASP,
перепроверить при реализации).

Требования: не короче 10 символов, проверка по списку скомпрометированных
через k-анонимный запрос к Have I Been Pwned. Никаких требований к составу
символов — они заставляют людей писать `Password1!` и не повышают стойкость.

### Ограничение попыток входа

По email и по IP: 5 попыток за 15 минут, затем экспоненциальная задержка.
Счётчик в Redis.

### Верификация email и восстановление пароля

Не в MVP: пользователь один, и он же владелец. Реализуется в M7 —
до появления внешних пользователей. Записано как блокирующий пункт
в [BACKLOG.md](BACKLOG.md).

До этого момента регистрация закрыта — см. раздел 7.

## 3. Разграничение доступа

### Принцип

Проверка владения не должна быть обязанностью каждого обработчика.
Формулировка вида «проверять принадлежность чека в каждом эндпоинте» —
это гарантия, что рано или поздно где-то забудут. Один пропуск —
и данные утекли.

Поэтому ограничение по владельцу применяется **на уровне доступа к данным**,
а не в бизнес-логике.

### Реализация

Расширение Prisma-клиента автоматически добавляет `userId` текущего
пользователя в условие каждого запроса к таблицам, содержащим это поле:

```ts
const scopedPrisma = prisma.$extends({
  query: {
    $allModels: {
      async $allOperations({ model, operation, args, query }) {
        if (!USER_SCOPED_MODELS.has(model)) return query(args)
        const userId = requestContext.getUserId() // AsyncLocalStorage
        args.where = { ...args.where, userId, deletedAt: null }
        return query(args)
      },
    },
  },
})
```

Обработчик пишет `prisma.receipt.findUnique({ where: { id } })` и физически
не может получить чужую запись. Забыть фильтр невозможно, потому что
его никто не пишет вручную.

`userId` берётся из контекста запроса через `AsyncLocalStorage` — не передаётся
параметром, который тоже можно забыть.

Тем же расширением добавляется `deletedAt: null`, что закрывает вторую
типовую ошибку — показ удалённых записей.

### Обход ограничения

Фоновым задачам и регулярным операциям нужен доступ вне контекста пользователя.
Для них — отдельный клиент без расширения, доступный только в слое worker'а.
Разделение явное: два разных инжектируемых токена, и обычный код до неограниченного
клиента не дотягивается.

### Ответ на чужой ресурс

`404`, не `403`. Различие между «не существует» и «существует, но чужой»
сообщает, что такой чек есть — это утечка.

## 4. Загрузка файлов

**Тип определяется по сигнатуре файла**, а не по `Content-Type` и не по
расширению. Оба задаются клиентом. Проверяются первые байты содержимого.

**Размер ограничивается на уровне сервера**, до чтения тела в память.

**Изображение перекодируется.** Загруженный файл не сохраняется как есть:
он декодируется, к нему применяется поворот из EXIF, и он кодируется заново
в JPEG. Это заодно уничтожает любую полезную нагрузку, спрятанную в контейнере
исходного файла, и удаляет метаданные — включая GPS-координаты, которые
камера телефона записывает по умолчанию и которые здесь совершенно не нужны.

**Имя файла от клиента не используется.** Ключ объекта генерируется
из UUID: `receipts/{userId}/{receiptId}/original.jpg`.

**Частота ограничена:** 30 загрузок в час на пользователя. Защищает
и от случайного цикла в коде, и от исчерпания лимитов провайдера.

Антивирусной проверки нет: файлы никогда не выполняются, отдаются только
как изображения после перекодирования, и доступны только владельцу.

---

## 5. Хранилище

Бакет закрыт для публичного доступа. Ни один объект не имеет постоянной ссылки.

Интерфейс получает подписанные ссылки со сроком жизни 15 минут, вычисляемые
при каждом запросе. Ссылка, попавшая в историю браузера или в чужие руки,
протухает.

Ключи объектов содержат `userId` и UUID чека — угадать чужой ключ нельзя,
да и без подписи он бесполезен.

## 6. Персональные данные

Позиция и условия перехода зафиксированы в [ADR-0012](adr/0012-deferred-privacy-posture.md).
Здесь — практическая сторона.

### Что именно чувствительно

Чек раскрывает больше, чем кажется. Аптечный чек показывает состояние здоровья.
Набор магазинов и время покупок — маршруты и распорядок дня. Состав покупок —
привычки, состав семьи, доход.

Плюс отдельно: фотография чека содержит GPS-координаты в EXIF, если камера
их записывает. Поэтому перекодирование изображения при загрузке (раздел 4) —
это не только безопасность, но и приватность.

### Текущий режим: только свои чеки

Обрабатываются данные автора. Работа на бесплатном тарифе провайдера,
который может использовать запросы для обучения — осознанное решение
человека о своих данных.

Единственное требование: приложение не должно быть доступно снаружи
без аутентификации, а регистрация закрыта (раздел 7).

### Триггер: первый чужой чек

До того как чек загрузит другой человек, выполнить:

1. Запретить обучение на данных — параметр `data_collection: "deny"`
   в запросах либо переход на платного провайдера с обработкой в ЕС.
2. Включить удаление сырых ответов распознавания через 30 дней.
   Они содержат весь текст чека и хранятся дольше, чем нужно.
3. `DELETE /me` с реальным каскадом, включая объекты в хранилище.
4. `GET /me/export`.
5. Текст на регистрации: что храним, куда отправляем, как удалить.
6. Верификация email и восстановление пароля.

Пункты 3, 4 и 6 — обычные функции, нужные независимо от регулирования.
Пункты 1 и 2 — конфигурация. Реальной работы меньше, чем кажется.

### Что не логируется никогда

```text
изображения чеков
распознанный текст
пароли, их хеши, токены сессий
ключи провайдеров
email в открытом виде       — в логах идентификатор пользователя
IP-адрес в открытом виде    — хранится хеш
```

Сырой ответ провайдера лежит в хранилище с явным сроком жизни, а не в логах,
где срок хранения никем не контролируется.

Sentry настраивается с фильтрацией: тела запросов и cookie не отправляются.

## 7. Защита приложения на время проверки гипотезы

Пока пользователь один, простейшая защита — закрытая регистрация.

Переменная `REGISTRATION_ENABLED=false` отключает `POST /auth/register`
в production. Аккаунт создаётся один раз командой заполнения базы.

Это устраняет целый класс проблем разом: нет чужих аккаунтов — нет чужих
данных, нет злоупотребления лимитами провайдера, нет обязательств
по обработке персональных данных. Флаг снимается в M7 вместе
с выполнением пунктов из раздела 6.

## 8. Настройки бэкенда

**Helmet** с политикой безопасности содержимого. Для SPA она строгая:
`script-src 'self'`, без `unsafe-inline` и `unsafe-eval`.

**CORS** — список разрешённых источников из конфигурации, `credentials: true`.
Никаких `*`: с cookie-аутентификацией это неработоспособно и опасно.

**Ограничение частоты** на трёх уровнях: глобально по IP, по пользователю
на загрузку, отдельно жёстко на вход и регистрацию.

**Ограничение размера тела** — 1 МБ для JSON, отдельный лимит для загрузки файла.

**Валидация всего входящего** Zod-схемами, включая параметры строки запроса
и параметры пути.

**Защита от SQL-инъекций** обеспечивается Prisma. Единственное место риска —
`$queryRaw` в аналитике; там только параметризованные запросы, никакой
конкатенации строк.

## 9. Секреты

В репозитории — только `.env.example` с пустыми значениями и комментариями.
Реальные `.env` в `.gitignore`.

В production секреты задаются переменными окружения платформы.

Секреты не попадают в сборку фронтенда. В Nuxt доступны клиенту только
переменные с префиксом `NUXT_PUBLIC_`, и туда идёт только базовый URL API.
Ключи провайдеров существуют исключительно на бэкенде — SPA обращается
к провайдеру только через свой API, никогда напрямую.

Проверка при старте: приложение падает, если обязательная переменная
не задана или пуста. Лучше отказ при запуске, чем непонятная ошибка
на первом же чеке.
