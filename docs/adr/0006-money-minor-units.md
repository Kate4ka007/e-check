# ADR-0006 — Деньги в минорных единицах

**Статус:** принято
**Дата:** 2026-08-30

## Контекст

Приложение о деньгах. Числа с плавающей точкой для денег дают накопительную
ошибку: `0.1 + 0.2 !== 0.3`. На чеке из тридцати позиций это приводит к тому,
что сумма позиций не сходится с итогом на копейку — и приложение показывает
предупреждение об ошибке там, где ошибки нет.

В первой версии плана это решение было записано, но примеры данных и модель
всё равно использовали дробные числа. Здесь противоречие снимается.

## Решение

Все денежные величины — целое число минорных единиц валюты плюс код валюты.
2,78 EUR хранится как `278` и `"EUR"`.

Поля именуются с суффиксом `Minor`: `totalMinor`, `unitPriceMinor`, `subtotalMinor`.
Суффикс обязателен — он делает ошибку размерности видимой при чтении кода.

Тип в Prisma — `Int`. В JSON — целое число, не строка.

Количество знаков после запятой берётся из метаданных ISO 4217, а не хардкодится
делением на 100: у JPY знаков нет, у BHD их три. Форматирование — через
`Intl.NumberFormat`, который эти правила уже знает.

Арифметика — только над целыми. Округление при разделении сумм выполняется
явно и в одном месте.

## Альтернативы

**`Decimal(12,2)` в PostgreSQL и decimal-библиотека в коде** — тоже корректно
и читается естественнее. Не выбрано, потому что Prisma отдаёт `Decimal` как
объект, который нужно сериализовать на каждой границе, и потому что дробность,
зашитая в тип колонки, не универсальна для всех валют.

**Числа с плавающей точкой** — некорректно.

## Последствия

Арифметика точна. Сравнения работают. Сверка суммы позиций с итогом даёт
осмысленный результат.

Плата — преобразование на каждой границе. Смягчается тем, что преобразование
живёт ровно в двух местах: Zod-схемы контрактов и функция форматирования
в интерфейсе.

## Когда пересмотреть

Не пересматривать.
