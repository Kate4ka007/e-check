# ADR-0009 — Zod вместо class-validator

**Статус:** принято
**Дата:** 2026-08-30

## Контекст

Форма данных на границе API нужна в четырёх местах:

1. Валидация входящих запросов на бэкенде.
2. Типы ответов на фронтенде.
3. Валидация формы в редакторе чека.
4. Валидация JSON, который вернула модель распознавания.

Первая версия плана предлагала `class-validator` для первого пункта и
отдельный пакет с типами для второго. Такой пакет расходится с реальными DTO
через пару недель — и тогда типы начинают врать, что хуже отсутствия типов.
Четвёртый пункт не был закрыт ничем.

## Решение

Zod-схемы в `packages/contracts` — единственное определение формы данных.

- Бэкенд: `nestjs-zod` превращает схему в pipe валидации.
- Фронтенд: `z.infer` даёт тип, форма валидируется той же схемой.
- Распознавание: ответ модели проверяется той же схемой позиций чека.
- Документация: `zod-to-openapi` генерирует OpenAPI из тех же схем.

Расхождение между API и фронтендом становится ошибкой компиляции.

## Альтернативы

**class-validator + DTO-классы** — идиоматично для NestJS, но схема живёт
в декораторах класса и на фронтенд не переносится. Плюс требует
`reflect-metadata` и экспериментальных декораторов.

**Генерация клиента из OpenAPI** — рабочий вариант, но добавляет шаг сборки
и даёт только типы, без переиспользуемой рантайм-валидации.

**Ручной пакет типов** — расходится с реальностью и создаёт ложную уверенность.

## Последствия

Одно определение вместо четырёх. Валидация ответа модели получается бесплатно —
именно та задача, для которой Zod подходит идеально.

Плата — отход от идиоматики NestJS. Разработчик, привыкший к `class-validator`,
удивится. Для соло-проекта не имеет значения.

## Когда пересмотреть

Если `nestjs-zod` перестанет поддерживаться — перейти на ручной pipe поверх
тех же схем. Сами схемы при этом не меняются, что и есть смысл решения.
