Главный документ проекта. Содержит цели, границы, архитектуру верхнего уровня и план работ.
Детали вынесены в отдельные документы — ссылки по тексту.

Версия 2. Предыдущая версия сохранена в [archive/PROJECT_PLAN.v1.md](archive/PROJECT_PLAN.v1.md).

---

## 1. Что это и зачем

Веб-приложение, которое превращает фотографию чека в структурированные данные о расходах.

Пользователь фотографирует чек → приложение распознаёт магазин, дату, позиции и суммы →
пользователь проверяет и исправляет → чек сохраняется → расходы видны в истории и аналитике.

### Проверяемая гипотеза

Проект находится на стадии проверки гипотезы, а не разработки продукта. Гипотеза формулируется так:

> Автоматическое распознавание чеков достаточно точное, чтобы исправлять результат было
> быстрее, чем вводить данные руками. Если это так — учёт расходов перестаёт быть рутиной,
> которую забрасывают через две недели.

Всё остальное в этом документе имеет смысл только если гипотеза верна. Поэтому работа начинается
не с кода приложения, а с измерения точности на реальных чеках — см. [M0](#m0--проверка-гипотезы).

### Критерий проверки

Гипотеза считается подтверждённой, если на выборке из 30–50 реальных чеков:

- магазин, дата и итоговая сумма распознаны верно не реже чем в 90% случаев;
- позиции чека (название + цена) распознаны верно не реже чем в 80% случаев;
- исправление одного чека вручную занимает менее 30 секунд.

Пороги выбраны как рабочая гипотеза и могут быть скорректированы по результатам M0 —
но скорректированы осознанно и с записью причины, а не задним числом под полученный результат.

## 2. Границы

### Входит в MVP

Регистрация и вход. Загрузка чека с камеры или файлом. Асинхронное распознавание.
Экран проверки и правки распознанного. Ручной ввод чека, если распознавание не удалось.
История чеков с фильтрами. Категории (системные). Аналитика: сумма за период, разбивка
по категориям и магазинам, динамика по времени. Удаление аккаунта и экспорт данных.

### Не входит в MVP

Банковские интеграции и Open Banking. Совместные семейные счета. Бюджеты и регулярные платежи.
Пользовательские категории. Расходы без чека. Нативные мобильные приложения. Offline-режим.
Мультивалютная конвертация. Прогнозная аналитика. Полноценный бухгалтерский учёт.

### Сознательно упрощено относительно версии 1 плана

Проект делает один человек без дедлайна для проверки гипотезы, поэтому из первоначального
плана убрано то, что стоит дорого и не приближает ответ на главный вопрос:

| Убрано                          | Вместо этого                           | Когда вернуть                       |
| ------------------------------- | -------------------------------------- | ----------------------------------- |
| Turborepo                       | Просто pnpm workspace                  | Когда сборка станет медленной       |
| Staging-окружение               | local + production                     | Перед первым внешним пользователем  |
| Testcontainers                  | Тестовая БД в docker compose           | Если тесты начнут мешать друг другу |
| Собственный UI-кит              | Nuxt UI                                | Не возвращать                       |
| Полная пирамида тестов          | Точечные unit + один сквозной сценарий | По мере роста числа регрессий       |
| CRUD пользовательских категорий | Только системные категории             | Phase 2                             |
| Отдельная сущность Expense      | Расходы выводятся из позиций чека      | Когда понадобится расход без чека   |
| Полный audit trail              | Поле `source` у изменённых полей       | Когда появятся внешние пользователи |

## 4. Архитектура

```text
                        ┌──────────────────────┐
                        │   Nuxt (браузер)     │
                        │  сканер · редактор   │
                        │  история · аналитика │
                        └───────────┬──────────┘
                                    │ REST + cookie-сессия
                        ┌───────────▼──────────┐
                        │       NestJS API     │
                        │  auth · receipts     │
                        │  categories          │
                        │  analytics           │
                        └────┬─────────────┬───┘
                             │             │
                   ┌─────────▼───┐   ┌─────▼──────┐      ┌──────────────┐
                   │ PostgreSQL  │   │   Redis    │      │Object storage│
                   └─────────────┘   └─────┬──────┘      │ MinIO → R2   │
                                           │             └───────┬──────┘
                                    ┌──────▼──────┐              │
                                    │   Worker    │◄─────────────┘
                                    │  (тот же    │  читает изображение
                                    │  код, свой  │
                                    │  entrypoint)│
                                    └──────┬──────┘
                                           │
                                  ┌────────▼─────────┐
                                  │ ReceiptExtractor │
                                  ├──────────────────┤
                                  │ vision-модель    │  один вызов
                                  │        или       │
                                  │ OCR + парсер     │  два этапа
                                  └──────────────────┘
```

API и worker — один и тот же кодовая база с разными точками входа. Разделять на отдельные
приложения незачем: они делят Prisma-клиент, конфигурацию и доменную логику. Масштабировать
их независимо это не мешает — запускаются они как разные процессы.

Какой вариант `ReceiptExtractor` останется — решается по результатам M0.
Подробности в [PROCESSING_PIPELINE.md](PROCESSING_PIPELINE.md).

```text
receipt-tracker/
├── apps/
│   ├── web/                 Nuxt: HTML для `/` и `/demo`, SPA за сессией
│   └── api/                 NestJS: API и worker
│       └── src/
│           ├── main.ts              точка входа API
│           ├── worker.ts            точка входа worker
│           ├── auth/
│           ├── users/
│           ├── receipts/
│           ├── processing/          оркестрация распознавания
│           ├── extraction/          провайдеры распознавания
│           ├── categories/
│           ├── analytics/
│           ├── storage/
│           ├── common/
│           └── config/
├── packages/
│   └── contracts/           Zod-схемы и выводимые из них типы
├── infrastructure/
│   └── docker/
├── spike/                   одноразовые скрипты M0, не продакшн-код
└── docs/
```

`packages/contracts` — единственное место, где определяется форма данных на границе API.
Бэкенд валидирует ими входящие запросы, фронтенд получает из них типы. Расхождение
между тем, что API отдаёт, и тем, что фронтенд ожидает, становится ошибкой компиляции.

## 7. Фронтенд

### Страницы

```text
/                      дашборд: месяц, сравнение с прошлым, топ категорий, последние чеки
/login  /register      вход и регистрация
/receipts              история с поиском и фильтрами
/receipts/new          сканер: камера или файл
/receipts/:id          просмотр и редактирование чека
/analytics             разбивки и динамика
/settings              профиль, экспорт данных, удаление аккаунта
```

### Экран проверки чека

Ключевой экран продукта — от его удобства зависит ответ на гипотезу. На широком экране
изображение и данные рядом, на узком — вертикально, изображение сворачивается в превью.

```text
┌───────────────────┬────────────────────────────┐
│                   │ Магазин   [LIDL          ] │
│                   │ Дата      [28.08.2026    ] │
│    изображение    │ Валюта    [EUR           ] │
│      чека         │                            │
│   (зум, поворот)  │ Позиции                    │
│                   │  ┌──────────────────────┐  │
│                   │  │ MILCH  1 × 1,29  Еда │  │
│                   │  │ BROT   1 × 1,49  Еда │  │
│                   │  └──────────────────────┘  │
│                   │  + добавить позицию        │
│                   │                            │
│                   │ Итого     [2,78          ] │
│                   │ ⚠ сумма позиций сходится   │
│                   │                            │
│                   │        [ Сохранить ]       │
└───────────────────┴────────────────────────────┘
```

Требования к экрану:

- Редактируется любое поле. Распознавание — это черновик, а не результат.
- Поля с низкой уверенностью визуально помечены, но сохранение не блокируют.
- Расхождение суммы позиций с итогом показывается как предупреждение, а не ошибка:
  на реальных чеках бывают округления, скидки на весь чек и нераспознанные строки.
- Тот же экран открывается пустым при ручном вводе — отдельной формы нет.

### Состояния загрузки

У каждого асинхронного действия четыре состояния: `idle`, `loading`, `success`, `error`.

Для распознавания прогресс показывается по-человечески — «Читаем чек…», «Разбираем позиции…» —
а не как технические статусы `OCR_COMPLETED`. Ошибки формулируются действием, которое
может предпринять пользователь: не «Internal Server Error», а «Не удалось прочитать чек.
Попробуйте переснять при лучшем освещении или введите данные вручную».

## 8. Бэкенд

### Модули

| Модуль       | Ответственность                                                      |
| ------------ | -------------------------------------------------------------------- |
| `auth`       | регистрация, вход, сессии, ротация refresh-токенов, guard'ы          |
| `users`      | профиль, экспорт данных, удаление аккаунта                           |
| `receipts`   | CRUD чеков и позиций, проверка владения, фильтры и пагинация         |
| `processing` | оркестрация: постановка задачи, статусы, ретраи, повторная обработка |
| `extraction` | реализации `ReceiptExtractor`, включая моки                          |
| `categories` | системные категории, сопоставление ответа модели с ними              |
| `analytics`  | агрегаты для дашборда                                                |
| `storage`    | загрузка в S3, подписанные ссылки, удаление объектов                 |

Границы модулей совпадают с границами документации: `processing` и `extraction` описаны
в [PROCESSING_PIPELINE.md](PROCESSING_PIPELINE.md), `auth` и `users` —
в [SECURITY_AND_PRIVACY.md](SECURITY_AND_PRIVACY.md).

### Сквозные требования

Все входящие данные валидируются Zod-схемами из `packages/contracts`. Ответы об ошибках
имеют единый формат со стабильным машиночитаемым кодом — фронтенд реагирует на `code`,
а не разбирает текст. Каждый запрос и каждая фоновая задача имеют `requestId`, который
проходит через все логи. Доступ к чужим данным невозможен на уровне слоя доступа к БД,
а не за счёт внимательности в каждом обработчике.

Детали — в [API_SPEC.md](API_SPEC.md) и [SECURITY_AND_PRIVACY.md](SECURITY_AND_PRIVACY.md).

## 9. Майлстоуны

Порядок подчинён одному правилу: **риск проверяется раньше, чем в него вкладывается работа.**

### M0 — проверка гипотезы

Самый важный этап. Его цель — узнать за неделю то, ради чего иначе пришлось бы писать
три месяца кода.

Собрать 30–50 своих реальных чеков — разных магазинов, включая мятые, длинные и с плохой
печатью. Написать одноразовый скрипт в `spike/`, который прогоняет их через три варианта:
vision-модель одним вызовом, OCR плюс текстовый парсер, и — если готовы завести аккаунт —
Azure `prebuilt-receipt` как эталон. Разметить ожидаемый результат руками. Посчитать точность
по полям и время на исправление.

Параллельно — «скелет»: пустое приложение, поднятое локально и задеплоенное в production.
Не для того, чтобы что-то показать, а чтобы деплой не оказался сюрпризом на последнем месяце.

**Результат:** число, отвечающее на вопрос «стоит ли это делать», и работающий деплой.
Если точность существенно ниже порогов из раздела 1 — честно остановиться или сменить подход.

### M1 — фундамент

NestJS с конфигурацией, Prisma, PostgreSQL. Модель пользователя, регистрация, вход, сессии.
Глобальная валидация, единый формат ошибок, `requestId`. Nuxt, layout, страницы входа,
API-клиент, middleware маршрутов. Структурные логи с `requestId` — сразу, а не в конце: без них
отладка асинхронного распознавания превращается в гадание.

**Результат:** пользователь регистрируется и входит, ошибки видны в логах API.

### M2 — загрузка чека

Модель чека. Загрузка изображения в MinIO. Валидация файла, включая конвертацию HEIC —
это формат камеры iPhone по умолчанию, без него часть чеков просто не загрузится.
Уменьшение изображения перед отправкой в модель. Дедупликация по хешу. Ограничение частоты
загрузок. Постановка задачи в очередь. На фронте — камера, выбор файла, превью, прогресс.

**Результат:** чек загружается и попадает в очередь на обработку.

### M3 — распознавание

Worker. `ReceiptExtractor` с реализацией, победившей в M0, плюс мок для тестов.
Перебор моделей при отказе провайдера, разделение ошибок на повторяемые и окончательные,
сохранение сырого ответа. Вычисление уверенности. Статус обработки на фронте.

**Результат:** загруженный чек превращается в структурированные данные.

### M4 — проверка и сохранение

Экран редактирования: поля, позиции, категории, сверка сумм, пометки низкой уверенности.
Ручной ввод при сбое распознавания. Сохранение с валидацией на бэкенде.

**Результат:** сквозной сценарий работает целиком — от фотографии до сохранённого чека.
С этого момента приложением уже можно пользоваться.

### M5 — история

Список чеков, пагинация, поиск, фильтры по датам, категориям и магазинам. Удаление.

### M6 — аналитика

Сумма за период, сравнение с предыдущим, разбивка по категориям и магазинам, динамика,
выбор диапазона дат. Дашборд.

**Результат:** MVP собран. Дальше — использование и наблюдение за метриками.

### M7 — подготовка к внешним пользователям

Выполняется только если решено идти дальше. Переключение на платного EU-провайдера
или запрет обучения на данных. Экспорт и удаление данных. Текст о персональных данных.
Верификация email и восстановление пароля. Ограничения частоты запросов. Резервное копирование.

Подробности — в [SECURITY_AND_PRIVACY.md](SECURITY_AND_PRIVACY.md) и [ADR-0012](adr/0012-deferred-privacy-posture.md).

## 10. Готовность MVP

MVP готов, когда проходит сквозной сценарий:

```text
регистрация → вход → загрузка чека → ожидание обработки →
проверка распознанного → правка → сохранение →
чек виден в истории → расход виден в аналитике
```

и выполняются условия:

- при сбое распознавания чек можно ввести вручную, а не потерять;
- повторная загрузка того же файла не создаёт дубликат;
- повторная обработка обновляет существующий чек, а не плодит новые;
- суммы в аналитике сходятся с суммами чеков;
- сквозной сценарий покрыт автотестом;
- ошибки провайдера не роняют приложение и понятно объясняются пользователю.

## 11. Метрики

Считать с первого дня использования, иначе непонятно, работает ли гипотеза.

| Метрика                            | Зачем                                                                 |
| ---------------------------------- | --------------------------------------------------------------------- |
| `manual_correction_rate`           | доля полей, исправленных вручную — прямая мера качества распознавания |
| Время от загрузки до сохранения    | если больше минуты, ручной ввод удобнее                               |
| Доля чеков, дошедших до сохранения | сколько теряется на сбоях и на полпути                                |
| Длительность обработки, p50 и p95  | терпимо ли ждать                                                      |
| Чеков в неделю                     | пользуется ли человек этим на самом деле                              |

Главная метрика — последняя. Если через месяц вы сами перестали загружать чеки,
гипотеза не подтвердилась, какой бы ни была точность.

---

## 12. Принципы

**Распознавание асинхронно.** HTTP-запрос не ждёт модель.

**Модель не источник истины.** Она предлагает черновик, бэкенд проверяет, пользователь подтверждает.

**Деньги считает код.** Арифметика — в доменной логике, целыми числами, никогда в модели.

**Провайдеры заменяемы.** Смена модели — правка конфигурации, а не рефакторинг.

**Бизнес-правила на бэкенде.** Фронтенд может дублировать проверку ради удобства,
но никогда не быть её единственным местом.

**Функции делаются вертикально.** Каждая проходит через весь стек целиком, а не «сначала весь бэкенд».

**Сначала измерить.** Наблюдаемость раньше оптимизации, точность раньше архитектуры.

---

## 13. Что дальше, если гипотеза подтвердится

Порядок отражает ожидаемую ценность, а не сложность.

**Ближайшее:** пользовательские категории, расходы без чека, экспорт в CSV, бюджеты,
нормализация названий магазинов.

**Затем:** подсказки категорий на основе истории, обнаружение дубликатов по содержимому,
история цен на товары, регулярные расходы.

**Дальше:** совместные семейные счета, уведомления, улучшения PWA.

**Отдалённое:** банковские интеграции, помощник по расходам на основе проверенных агрегатов —
но никогда не позволяющий модели самой считать суммы.
