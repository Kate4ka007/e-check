# M0 — замер точности распознавания

Одноразовые скрипты. **Это не production-код** — после M0 всё содержимое
каталога выбрасывается, а выводы переезжают в `docs/`.

Цель: получить число, отвечающее на вопрос «распознаются ли чеки достаточно
хорошо, чтобы продуктом имело смысл пользоваться». Пороги — в
[PROJECT_PLAN.md](../docs/PROJECT_PLAN.md), раздел 1.

---

## Быстрый старт

```bash
cd spike
pnpm install

cp .env.example .env          # вписать OPENROUTER_API_KEY
pnpm models                   # узнать доступные модели, вписать в .env

# положить чеки в fixtures/private/ как 001.jpg, 002.jpg, ...

pnpm annotate                 # создать шаблоны разметки
# заполнить fixtures/private/*.expected.json вручную

pnpm run                      # прогнать через модель
pnpm score                    # посчитать точность
```

---

## Команды

| Команда                                       | Что делает                                    |
| --------------------------------------------- | --------------------------------------------- |
| `pnpm models`                                 | бесплатные vision-модели, доступные сейчас    |
| `pnpm models -- --text`                       | бесплатные текстовые модели                   |
| `pnpm annotate`                               | создать пустые шаблоны разметки               |
| `pnpm models`                                 | список доступных бесплатных моделей           |
| `pnpm check <модель> ...`                     | жива ли модель: один дешёвый запрос           |
| `pnpm extract`                                | прогнать чеки на моделях из `.env`            |
| `pnpm extract -- --models openai/gpt-4o-mini` | конкретная модель, минуя `.env`               |
| `pnpm extract -- --kind two-stage`            | двухэтапный вариант: OCR, затем разбор текста |
| `pnpm extract -- --force`                     | игнорировать кэш                              |
| `pnpm extract -- --only 001`                  | только один чек                               |
| `pnpm inspect`                                | форматы полей в ответах, причины отказов      |
| `pnpm diff`                                   | чем модели разошлись между собой              |
| `pnpm score`                                  | таблица сравнения всех прогонов               |
| `pnpm score -- --details`                     | плюс разбор ошибок                            |
| `pnpm score -- --pick <тег>`                  | подробности конкретного прогона               |

Скрипт называется `extract`, а не `run`: `pnpm run` — встроенная команда
самого pnpm, она бы перехватила вызов.

## Сравнение моделей

Прогоны не перетирают друг друга: модель входит в ключ кэша. Поэтому
достаточно прогнать несколько раз и один раз посчитать.

```bash
pnpm extract                                    # бесплатные из .env
pnpm extract -- --models openai/gpt-4o-mini     # платная
pnpm extract -- --kind two-stage                # двухэтапный вариант
pnpm diff                                       # в чём разошлись
pnpm score                                      # таблица сравнения
```

`pnpm diff` дополнительно проверяет, сходится ли сумма позиций с итогом
чека. Это сильный признак правоты без обращения к самому чеку: пропуск
или выдуманная строка почти всегда ломают равенство.

### Рассуждения отключены

В запросах стоит `reasoning: { enabled: false }`. Чтение чека — задача
распознавания, а не рассуждения, и размышление только съедает лимит
вывода: до отключения модель тратила 28 тысяч символов на размышления
и до ответа не добиралась. После — 9 секунд на чек вместо 575.

`pnpm score` группирует результаты по варианту, версии промпта и модели
и сортирует по точности позиций. Подробный разбор печатается для лучшего
прогона; другой выбирается через `--pick`.

### Платные модели

Скрипт спрашивает подтверждение перед прогоном на платной модели
и печатает фактическую стоимость после — она приходит от OpenRouter,
а не оценивается.

Платные модели требуют пополнения баланса. Минимальные $10 заодно
поднимают дневной лимит бесплатных моделей с 50 до 1000 запросов
навсегда — то ограничение, в которое упирается отладка промпта.

`fixtures/private/` и `results/` в `.gitignore`: реальные чеки — персональные
данные, а ответы моделей содержат их полный текст.

## Почему всё устроено именно так

### Модель не считает деньги

Суммы запрашиваются строкой ровно как напечатано на чеке — `"2,78"`.
Перевод в минорные единицы делает `money.ts`.

Просить модель вернуть `278` означало бы просить её умножить на сто.
Это арифметика, а арифметику в этом проекте выполняет код
([Принцип 3](../docs/PROJECT_PLAN.md)). Заодно снимается вопрос
локальных разделителей: `1.234` в немецком чеке — это тысяча
двести тридцать четыре, и разбирать такое надёжнее детерминированным кодом.

### Результаты кэшируются

Бесплатный тариф OpenRouter даёт 50 запросов в день. При отладке промпта
один чек прогоняется десятки раз, и без кэша дневная квота уходит за полчаса.

Ключ кэша включает хеш изображения, вариант извлечения и версию промпта.
Правка промпта автоматически обесценивает кэш — иначе после изменения
результат не поменялся бы, и было бы непонятно почему.

### Моделей несколько

Бесплатные модели ротируются: работавшая вчера сегодня отдаёт
`404 No endpoints found`. `VISION_MODELS` — список кандидатов, при отказе
берётся следующий. Перезапускайте `pnpm models`, когда все начнут падать.

### Три способа получить JSON

Не все бесплатные модели поддерживают structured output. Скрипт пробует
по убыванию надёжности: `json_schema` → `json_object` → обычный текст
с выковыриванием JSON из ответа. Какой сработал, видно в результатах.

### Разметку лучше делать руками

Есть режим `pnpm annotate -- --from-result vision`, заполняющий шаблон
ответом модели. Он экономит время, но искажает измерение: глядя на готовый
ответ, легко пропустить ошибку, которую заметили бы при наборе с нуля.

Для первых чеков наберите руками. Это скучно и это самая важная часть M0 —
без честного эталона «точность» останется ощущением, а не числом.

## Что означают метрики

| Метрика            | Смысл                                                         |
| ------------------ | ------------------------------------------------------------- |
| Ответ прошёл схему | доля чеков, где модель вернула структурно корректный JSON     |
| Все три ключевых   | магазин, дата и итог верны одновременно                       |
| Найдено            | доля позиций эталона, которые модель нашла                    |
| Название + цена    | доля позиций, где верно и то и другое — практический критерий |
| Выдумано           | позиции, которых на чеке нет                                  |

**Выдуманные позиции хуже пропущенных.** Пропуск человек заметит, сверяя
итог. Выдуманную строку с правдоподобной ценой — нет. Если это число
не равно нулю, промпт надо править в первую очередь.

Сопоставление позиций идёт по похожести названий, а не по порядку:
одна пропущенная строка сдвинула бы всё остальное при сравнении по индексу.

---

## Ограничение выборки

На трёх чеках метрики показывают, что конвейер работает, но не насколько
он точен. Один неудачный чек — это минус 33% в таблице.

Для вывода о гипотезе нужно 30–50 чеков разных магазинов, включая заведомо
трудные: мятые, выцветшие, длинные, снятые при плохом свете. Скрипт при
малой выборке об этом предупреждает.
